# Fernet direct-key deployment mode

Refs #210. The gateway encrypts stored secrets (provider credentials, OAuth
tokens, catalog connection material) with a Python-compatible Fernet
implementation in `crates/aether-crypto/src/python_fernet.rs`. The configured
secret is interpreted in one of two modes, and production deployments should
use the **direct-key mode** described here.

## Two key modes

`derive_python_fernet_key` (`python_fernet.rs:303-310`) accepts the configured
secret and returns the 32-byte Fernet key, URL-safe Base64 encoded:

1. **Passphrase mode (legacy default).** Any value that does not decode as
   Base64 to exactly 32 bytes is run through PBKDF2-HMAC-SHA256 with the fixed
   application salt `SHA-256("aether-v1")[..16]` and 100,000 iterations
   (`python_fernet.rs:371-403`). The salt is a Python-compatibility hard
   constraint: test vectors pin the derived key, so it cannot be changed
   without breaking existing ciphertext. Every deployment shares this salt,
   which is acceptable only because the passphrase itself is the secret.
2. **Direct-key mode (recommended).** If the configured value is Base64
   (URL-safe or standard) that decodes to exactly 32 bytes
   (`decode_direct_fernet_key`, `python_fernet.rs:405-417`), those bytes are
   used directly as the Fernet key and PBKDF2 is bypassed entirely.

Direct-key mode is the recommended deployment posture:

- The encryption key is a standalone 256-bit random value with no passphrase
  semantics, no shared fixed salt, and no KDF cost at startup.
- Rotation becomes a well-defined operation: a new random direct key replaces
  the old one while the old key remains configured as a decryption fallback
  (see `fernet-encryption-key-rotation.md`). Passphrase-mode rotations would
  depend on the PBKDF2 derivation chain instead.
- Key custody is explicit: the exact bytes that encrypt the data are the same
  bytes you back up and rotate, which simplifies offline verification.

## Generating a direct key

Generate 32 random bytes and Base64-encode them:

```sh
openssl rand -base64 32
```

The output is 44 characters of padded standard Base64, for example
`d0rD9...=`. Properties the installer/runtime rely on:

- Padded Base64 decodes to exactly 32 bytes, which selects direct-key mode.
  An **unpadded** value is intentionally treated as a passphrase for Python
  compatibility (`python_fernet.rs:296-302`), so do not strip the padding or
  post-process the output.
- Standard and URL-safe Base64 are both accepted. `openssl rand -base64`
  emits standard Base64; this is fine.
- The value must contain at least 32 characters/bytes as configured:
  `validate_gateway_data_encryption_key` rejects values under 32 bytes and
  known published development/example values (`main.rs:141-160`).
- Keep the value a single line with no surrounding quotes or whitespace in the
  env file.

## Configuring the gateway

Single-node systemd/launchd installs keep secrets in
`/etc/aether/aether-gateway.env` (mode `0600`, or `0640` when the install
grants the service group read access; generated by `install.sh`).
Docker Compose installs keep them in the env file referenced by the compose
project. Set the gateway-specific variable; the legacy `ENCRYPTION_KEY`
remains only as a compatibility fallback:

```sh
AETHER_GATEWAY_DATA_ENCRYPTION_KEY=d0rD9...=
# ENCRYPTION_KEY=<old value, while migrating or rotating>
```

Resolution order (`main.rs:898-910`): `--data-encryption-key` /
`AETHER_GATEWAY_DATA_ENCRYPTION_KEY` wins; a non-empty `ENCRYPTION_KEY` is
used only when the gateway-specific value is unset. When both are set and
differ, startup logs a warning and prefers the gateway-specific value.

After editing the env file, restart the service (systemd
`systemctl restart aether-gateway`, launchd `launchctl kickstart`, or the
compose equivalent). The key is read at process startup; a running gateway
never re-reads it.

## Verifying direct-key mode

There is no runtime log line announcing the mode (the key itself is never
logged). Verify behavior instead:

1. Startup succeeds in `production` environment — a missing data encryption
   key fails startup there (`main.rs:163-171`).
2. Create a provider credential in the admin UI, then confirm the stored
   value is double-Base64 Fernet (wrapped tokens start with `Z0FBQUFB`,
   detected by `looks_like_python_fernet_ciphertext`) and decrypts with your direct key
   using the backup tool or a small `aether-crypto` harness.
3. A wrong key must fail closed: decrypting the same ciphertext with a
   different 32-byte value raises `InvalidTokenSignature`.

## Migrating from passphrase mode

1. Generate the new direct key as above.
2. Set `ENCRYPTION_KEY=<current passphrase>` if it is not already the
   configured value, and set `AETHER_GATEWAY_DATA_ENCRYPTION_KEY=<new direct
   key>`.
3. Restart. New writes encrypt with the direct key. Existing ciphertexts are
   still readable because passphrase-derived decryption is attempted via the
   fallback chain (`fallback_encryption_keys`,
   `snapshot_mapping.rs:228-244`, plus the catalog equivalent
   `decrypt_catalog_secret_with_fallbacks`,
   `handlers/shared/catalog.rs:58-88`).
4. Leave the old passphrase configured until every remaining ciphertext has
   been rewritten (see the rotation runbook for the re-encryption options and
   their limits). Then remove the old value and restart again.

## What direct-key mode does not change

- Ciphertext format is unchanged: the same double-Base64 Fernet token with a
  fixed `0x80` version byte. Direct-key and passphrase-mode ciphertexts are
  indistinguishable on disk.
- Envelope versioning and purpose binding of provider credentials
  (`PROVIDER_CATALOG_CREDENTIAL_ENVELOPE_V2`) are unaffected.
- The backup/restore keyring and tunnel release signing keys are separate
  trust domains; this document only covers the gateway data encryption key.

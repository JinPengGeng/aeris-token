# Fork 定制管理规范（Patch & Customization Policy）

> 本 fork（JinPengGeng/aeris-token）跟踪上游 fawney19/Aether。
> 定制分两条轨道管理：**补丁轨道**（小修复，目标上游化、分叉归零）与**深度定制轨道**（fork 特有功能，接受受控分叉）。

## 0. 轨道判定

| | 补丁轨道 | 深度定制轨道 |
|---|---|---|
| 规模 | 单 PR、通常 <500 行 | 多 PR / 子系统级 |
| 上游意愿 | 可能收 | 不会收 / 不适用 |
| 分叉预期 | 临时（staging） | 可能长期 |
| 例子 | #93 watchdog、#119 模型同步 | 调度器系列、特有治理功能 |

拿不准时先按补丁轨道做；发现规模/依赖失控再升级为深度定制，禁止悄悄长成大分叉。

## 1. 补丁轨道纪律

- **单 PR 单补丁**：一个 PR 只做一件事，不与其它补丁纠缠。
- **测试钉住**：先写复现/回归测试再修复；测试确定性（事件/信号量同步，禁止墙钟时序）。
- **附加式优先**：新增函数/模块/分支优于侵入式改写；侵入不可避免时收敛到最小并注释。
- **可拆出**：任何时刻可独立 cherry-pick（给上游）、独立回退。

生命周期：

```
fork 修复并验证（急用先落地）
   → 给上游提 PR（根因 + 复现测试）
   → 上游合入 → 下次 sync 自动回销 → 关闭跟踪记录
   → 上游拒收/长期搁置 → 登记为「已知分叉点」，定期重评
```

## 2. 深度定制轨道纪律

- **模块自包含**：定制集中在独立模块/目录，通过明确的接缝（trait/config/feature flag）接入主干；禁止把定制逻辑织进上游热区函数内部。
- **开关隔离**：默认行为与上游一致；定制行为必须经显式配置开启，缺省不激活。
- **冲突归属**：每个深度定制有 owner 和跟踪 issue；每次 sync 的合并冲突由 owner 负责收敛，冲突反复出现时重评接缝设计。
- **可演进**：定期评估三条出路——上游原生吸收（删定制）、贡献给上游（拆 PR 上游化）、重构保留（接缝劣化时）。
- **验收红线**：任何时刻 main 必须保持「可与上游合并」——sync 的三方合并可解，不允许出现无法收敛的冲突堆。

## 3. 同步纪律

- 同步方式为**真合并**（merge commit，祖先连通）：每次 sync 按定制点做三方合并，冲突显式暴露；禁止整树覆盖式快照吞掉定制语义。
- `.github/upstream-sync-state.json` 的 `last_integrated_sha` 是同步点的唯一权威记录；GitHub 的 ahead/behind 显示仅供参考。
- 冲突解决原则：以上游为基座，逐定制点重新落位；语义冲突时以上游为准重设计定制。

## 6. 流程（与社区标准一致）

```
短特性分支 → PR（CI 必绿 + 分支最新）→ squash 合 main（同步 PR 除外，用 merge）→ 删分支
```

- 特性 PR 一律 squash，保持线性历史。
- 上游同步 PR 由自动化用 merge 合入（祖先连通，GitHub ahead/behind 如实）。
- 线性历史规则对同步自动化（Writer App）单独豁免，其余角色无例外。

# Fork 补丁管理规范（Patch Policy）

> 本 fork（JinPengGeng/aeris-token）跟踪上游 fawney19/Aether，定制只以**补丁**形式存在。
> 目标：fork 产品代码与上游的差异趋近于零。补丁是 staging 区，不是永久资产。

## 1. 补丁纪律

每个源码定制必须满足：

- **单 PR 单补丁**：一个 PR 只做一件事，不与其它补丁纠缠。
- **测试钉住**：先写复现/回归测试，再写修复；测试要确定性（事件/信号量同步，禁止墙钟时序）。
- **附加式优先**：优先新增函数/模块/分支，避免侵入式改写既有函数内部。侵入不可避免时，把改动点收敛到最小并加注释。
- **可拆出**：任何时刻都能被独立 cherry-pick（给上游）、独立回退。超过 ~500 行或含依赖链的定制，先拆设计再写码。

## 2. 补丁生命周期

```
fork 修复并验证（急用先落地）
   → 给上游提 PR（根因 + 复现测试，素材即 fork PR 的描述）
   → 上游合入 → 下次 sync 自动回销本地补丁 → 关闭跟踪记录
   → 上游拒收/长期搁置 → 登记为「已知分叉点」，定期重评
```

- 每个合入 main 的补丁必须在本文件 §4 的跟踪表中登记。
- 分叉点每季度重评一次：上游是否已原生覆盖 / 是否愿意收 / 是否还需保留。

## 3. 同步纪律

- 同步方式为**真合并**（merge commit，祖先连通），使每次 sync 按补丁点做三方合并，冲突显式暴露；禁止整树覆盖式快照吞掉补丁语义。
- `.github/upstream-sync-state.json` 的 `last_integrated_sha` 是同步点的唯一权威记录；GitHub 的 ahead/behind 显示仅供参考。
- 同步冲突的解决原则：以上游为基座，逐补丁重新落位；补丁与上游新能力冲突时，以上游语义为准重新设计补丁。

## 5. 流程（与社区标准一致）

```
短特性分支 → PR（CI 必绿 + 分支最新）→ squash 合 main（同步 PR 除外，用 merge）→ 删分支
```

- 特性 PR 一律 squash，保持线性历史。
- 上游同步 PR 由自动化用 merge 合入（祖先连通，GitHub ahead/behind 如实）。
- 线性历史规则对同步自动化（Writer App）单独豁免，其余角色无例外。
